1产品概述与设计目标

本系统是一个运行于本机的桌面程序，核心定位：为电脑上已有的 Agent（TRAE、ZCode 等）提供交流平台——让本机多个 Agent 像拉群一样进入同一个房间，互相交流、分工协同完成复杂工作。人类既是发起者与旁观者，也是最高仲裁者；文件保存在群内共享，命令同步广播给所有 Agent。

产品定位（2026-08-27 修订）：软件的首要服务对象是电脑上的 Agent。内置 LLM Agent 是对话与编排的补充形态，外部本机 Agent（TRAE / ZCode）经接入网关进群才是一等公民——没有人类逐条驱动时，Agent 之间也能自主接活、互聊、交付。

核心设计目标

  • 同步收到：一条命令通过消息总线异步扇出，所有在线 Agent 同时收到任务与完整房间上下文——无论是内置 Agent 还是外部接入的本机 Agent。
  • 协同工作：Agent 按排产单分工执行，互聊走群内 @提及，过程对人类全程透明。
  • 身份可定义：用户自主为每个 Agent 制定身份（职责、工具权限、风格），获得身份的 Agent 在群内显示标签，并严格只执行身份对应部分的工作。内部 Agent 与外部 Agent 共用同一套身份卡体系。
  • 人类最高优先级：人类消息拥有绝对优先权——AI 陷入逻辑死锁时可立即出言阻止，需求偏差时可随时修正，排产单即刻作废重排。
  • 记忆可沉淀：向量库承载多方记忆，跨会话可检索，公共与私有记忆严格隔离。
  • 本机优先：程序、后端服务、向量库、记忆数据全部不出本机；外部 Agent 经本地网关接入，通信不走公网。
一句话原则：一切皆消息（append-only 事件流），人类拥有最高仲裁权，编排者不执行、执行者不编排。

3系统总体架构

系统分四层：交互面、决策与编排、执行与产出、底座设施。一条实时消息总线贯穿所有参与者。整体形态为桌面程序（Tauri 2）+ 本地后端服务（FastAPI sidecar）。

进程模型

  • Tauri 主进程：仅负责窗口与 sidecar 生命周期——启动时拉起 FastAPI 子进程并做健康检查（就绪前显示启动屏），异常退出自动重启（退避策略），窗口关闭时终止子进程。Rust 侧不承载业务逻辑。
  • FastAPI sidecar：全部业务所在（总线、编排、事件流、记忆、网关），监听 127.0.0.1:8899，同端口托管前端静态资源；开发期浏览器可直接打开同一地址调试。
  • MVP 不打包：开发期以 cargo tauri dev 弹窗运行验证功能；安装包（NSIS/MSI）留到 MVP 验收通过后再做。

架构要点

  • 一切皆消息：人类输入、Agent 输出、文件引用、排产单、回执、中断指令统一进入 append-only 事件流，全程可回放。
  • 同步收到 = 异步扇出：总线把命令并发派发给每个订阅的 Agent（asyncio.gather），各带独立上下文并行执行。
  • 薄编排层：初版自研轻量运行时；可参考 AutoGen GroupChat 的发言轮转机制，LangGraph 作为生产化演进方向。
  • 前端布局（v1.2 冻结）：左侧全功能侧边栏承载交互与设置——房间/成员列表、身份卡图形化编辑器、LLM 模型设置、记忆检索、预算治理、命令输入框与 P0 快捷按钮，常用操作不离开当前房间；右侧工作台以群聊消息流为主体，文件工作区 / 任务进度 / 事件回放做成可切换底部面板。侧边栏可折叠给工作台让位。
  • 协议分层：MCP 管工具与文件访问（每个 Agent 只看见身份允许的工具视图）；A2A 协议出口预留，远期接入外部 Agent。
Agent 一等公民：执行层的「本机外部 Agent」经第 14 章接入网关进群后与内置 Agent 完全同权——同排产单投递、同身份卡约束、同事件流审计。房间内没有内置 LLM Agent 时系统照常运转，成为纯粹的外部 Agent 协作平台。

4消息协议设计

消息协议是整个系统的地基，第一版即冻结 schema 并带版本号。所有消息为 JSON，经 WebSocket 传输，落库于事件流。

4.1 消息类型

类型发送者语义优先级
interrupt人类最高优先级：中断 / 修正 / 终止，抢占一切P0
task人类下达任务目标，触发编排P1
dispatch编排层排产单：指定执行者、顺序、交付物P2
chatAgent/人类普通群聊 / @提及互聊P3
deliverAgent交付物：文件引用 + manifestP3
receipt编排层验收回执：通过 / 打回（含原因）P3
system系统熔断触发、越权拦截、预算告警P2

4.2 通用消息结构

{
  "msg_id": "uuid",
  "schema_version": "1.0",
  "room_id": "room_xxx",
  "type": "dispatch",
  "priority": 2,                  // 0=interrupt 最高
  "sender": { "kind": "orchestrator", "id": "ceo", "label": "总编排" },
  "mentions": ["agent_b"],          // @提及，定向投递
  "payload": { ... },              // 按类型定义
  "context_refs": ["msg_aaa"],     // 引用的历史消息/文件
  "parent_task_id": "task_xxx",
  "created_at": "2026-08-27T10:00:00+08:00"
}

4.3 排产单 payload（dispatch）

{
  "subtasks": [
    {
      "id": "st_1",
      "assignee": "agent_a",
      "identity_label": "调研员",
      "instruction": "检索竞品资料并写调研笔记",
      "depends_on": [],
      "deliverable": { "type": "file", "path": "workspace/research.md" },
      "budget": { "max_tokens": 80000, "max_turns": 6 }
    },
    {
      "id": "st_2",
      "assignee": "agent_b",
      "identity_label": "开发员",
      "instruction": "依据调研笔记实现原型页面",
      "depends_on": ["st_1"],
      "deliverable": { "type": "file", "path": "workspace/proto/index.html" }
    }
  ]
}
投递语义：总线按优先级队列派发——P0 立即抢占（中断当前生成），P1/P2 插队，P3 顺序。mentions 非空时仅定向投递给被 @者，但仍对所有旁观者可见。

5用户自定义身份与标签体系

身份即配置：用户为每个 Agent 编写身份卡，加载后 Agent 在群内获得可见标签，并严格只执行身份对应部分的工作。同一 LLM 加载不同身份卡即为不同“员工”。

5.1 身份卡结构（YAML/JSON 存库）

identity_id: backend-dev
label: 开发员                    # 群内显示的标签名
description: 负责后端实现与自测
persona: 严谨、先定接口再动手、不懂就问
responsibilities: [写代码, 改工作区文件, 自测]
tools_allow: [fs.write, fs.read, shell.run, git.*]
fs_scope: [workspace/src/**]     # 文件写权限边界
budget: { tokens_per_task: 200000, max_chat_turns: 6 }
handoff: 产出必须写入工作区并附 manifest
created_by: user_001
version: 3

5.2 运行机制

  • 入群绑定：用户把身份卡指派给 Agent A / B（可随时更换），Agent 头像旁显示标签徽标，发言携带标签前缀。
  • 上下文注入：身份卡的 description / persona / responsibilities 注入系统提示词；工具白名单生成该 Agent 的 MCP 工具视图。
  • 执行约束：收到排产单时校验 identity_label 匹配；越界请求（调用白名单外工具、写权限外文件）由总线层直接拒绝并记录，不靠提示词“劝”。
  • 图形化编辑器：身份卡以表单控件编辑（工具白名单勾选、fs_scope 填写、预算滑杆），附 YAML 源码视图，支持导入导出分享。
  • 身份即资产：身份卡独立建表、带作者与版本，支持导出分享——为远期“身份市场”预留。
防串味：多个身份卡不共享对话历史。每个 Agent 维护私有记忆，只有结论（而非全程闲聊）沉淀到房间级公共记忆。

6职位化自主编排

6.1 编排层级

层级角色职责MVP 是否启用
L0人类下目标、interrupt 仲裁、关键节点确认✔
L1CEO 总编排器拆解目标、生成任务分解图、跨部门仲裁、汇总✔
L2部门主管内部排产、验收、打回V2 引入
L3执行者 Agent按身份卡执行、互聊、交付✔（A/B 双 Agent）
黄金法则：编排者永不执行，执行者永不编排。小任务（3 个以内子任务）自动退化为单层排产，避免过度设计。

6.2 标准编排流程

  1. 用户下达 task → CEO 生成任务分解图（子任务+依赖+所需身份），先给用户确认（可配置为自动通过）。
  2. 确认后 CEO 发 dispatch 排产单 → 总线按依赖顺序投递。
  3. 执行者按排产单工作，互聊走群内 @提及（计入轮数预算）。
  4. 交付 deliver → 编排层验收 receipt：不合格打回（附原因，计入轮数），合格进入下一子任务。
  5. 全部完成 → CEO 汇总结果 + 成本报告，@人类查收。

6.3 发言权调度

  • 排产单内声明的执行顺序优先；单外自由 @提及为兜底，计入互聊轮数。
  • 硬性熔断：单任务互聊超 max_chat_turns 或 token 超预算 → system 消息中断并 @人类裁决。

7人类最高优先级机制

人类不是旁观者，而是系统的最高仲裁者。interrupt（P0）消息可抢占一切正在进行的 Agent 活动。

7.1 三档介入语义

档位命令示例系统行为
修正“方向不对，改成调研国内市场”当前子任务作废，CEO 基于新需求重排，已产出的有效交付物保留
暂停“都停一下”所有 Agent 挂起，状态快照入库，等待人类后续指令恢复
终止“这个任务取消”任务整体终止，事件流封存，成本结算归档

7.2 抢占实现

  • 总线为每个 Agent 维护生成句柄，P0 到达时立即 cancel 当前 LLM 流式生成。
  • 中断点之后的事件标记 invalidated: true，回放时可辨识。
  • 前端提供醒目的一键操作：停止全部 @某Agent 修正。

7.3 死锁自动求助

熔断触发（互聊超轮、预算见底、编排层反复打回同一子任务 ≥3 次）时，系统自动发 system 消息 @人类，附带死锁上下文摘要（谁和谁争、争了几轮、各自立场），等待人类一句话裁决。

设计红线：任何自动化路径都必须存在一条“人类一句话就能接管”的出口。熔断不是终点，移交人类才是。

8文件共享工作区

  • 存储：本地目录 + SQLite 元数据（V2 换 PostgreSQL / S3 兼容对象存储）。每个房间独立工作区目录。
  • 共享语义：文件不是聊天附件，而是共享上下文——Agent 交付物写入工作区并附 manifest，其他 Agent 按路径引用继续加工。
  • 冲突控制：写入带版本号乐观锁（读时记录 version，写时校验，冲突返回最新版本让 Agent 重写）；同一文件并发任务先写隔离目录再合并。
  • 权限：按身份卡 fs_scope 限定读写边界；MVP 阶段简化为“读共享、写归当前任务负责 Agent”。
  • 工具化：Agent 不直接碰文件系统，统一经 MCP 文件工具（fs.read / fs.write / fs.list），行为全部入事件流。

9多方记忆与向量库

9.1 记忆分层

层级内容可见性载体
会话短期当前任务对话窗口按身份隔离内存 / 事件流
房间级公共滚动摘要：结论、决议、接口约定全房间文本摘要 + 向量库
Agent 私有角色立场、历史偏好、个人笔记仅本 Agent向量库（私有 collection）
跨房间长期身份卡经验、可复用知识按身份卡授权向量库（V2）

9.2 向量库方案

  • 选型：Chroma / Qdrant 本地实例 + 本地中文友好 embedding 模型（如 bge-m3），记忆数据不出本机。
  • Collection 划分：room_{id}_public 与 agent_{id}_private 物理隔离，检索接口强制带身份鉴权。
  • 写入时机：任务验收通过时沉淀结论到公共记忆；Agent 可在交付时主动写私有笔记。闲聊不入库。
  • 检索注入：Agent 收到排产单时自动检索 top-k 相关记忆（如“上次类似任务的做法”“对方定的接口规范”），注入上下文，标注来源时间。
隔离红线：私有记忆检索权限与身份绑定，任何 Agent 无法读到他者私有记忆；公共记忆全员可查但写入需经编排层确认，防止错误结论污染。

10治理、安全与成本

  • 工具治理：白名单在总线层强制校验，越权调用拒绝 + 记录 + 前端提示。
  • 预算熔断：房间级 / 任务级 / Agent 级三层 token 预算；水位 80% 告警，100% 熔断并 @人类。
  • 成本仪表盘：实时显示房间 token 消耗、各 Agent 花费排行、单次任务预算水位——数据直接来自事件流。
  • 事件溯源：全量消息 + 工具调用 + 文件版本入流，支持按任务回放（“Agent 为什么吵起来”一键复盘）。
  • 密钥安全：LLM API Key 仅存服务端环境变量，前端零接触。

12MVP 开发路线

阶段目标验收标准
第 1 步桌面程序骨架 + 「1人 + 1Agent」群聊链路：Tauri 2 窗口拉起 FastAPI sidecar，左侧栏（房间列表+输入框）+ 右侧消息流布局，WS 房间 + LLM 流式回复 + 事件落库双击/命令启动弹桌面窗口；发消息有流式回复；重启程序后历史可恢复
第 2 步双 Agent + 身份卡：左栏身份卡编辑器 Tab、@提及、广播扇出、群内标签、interrupt 抢占（P0 快捷按钮）命令同步到达 A/B；标签正确显示；P0 可中断生成
第 3 步文件工作区：上传、预览、Agent 经 MCP 工具读写（右侧底部面板呈现文件树与版本）Agent 交付物落工作区，版本冲突可复现并被拦截
第 4 步编排闭环：CEO 拆目标→确认→排产单→验收 + 向量记忆 + 熔断完整跑通一个双 Agent 协作任务，死锁能自动求助
第 5 步本地 Agent 接入：MCP 网关上线，先联调 TRAE 再复制到 ZCode；「无人值守自动接活」实现为每实例可选开关TRAE 经网关收发消息并完成一次交付，越权被拦截；开关切换后两种模式行为均正确

V2 展望：部门主管层、跨房间记忆、A2A 接外部 Agent、身份卡市场、安装包分发（NSIS/MSI）。

关键决策（v1.1 已确认；v1.2 于 2026-08-27 追加冻结）

决策项结论
产品形态 v1.2桌面原生程序：Tauri 2 窗口壳 + FastAPI sidecar（127.0.0.1:8899，随程序启停），双击启动免浏览器；MVP 开发期以 cargo tauri dev 运行不打包，安装包留到 MVP 验收后。Rust 仅管窗口与进程生命周期，业务全部在 Python 后端。
前端布局 v1.2左侧全功能侧边栏 + 右侧工作台：左栏放房间/成员、身份卡编辑器、LLM 设置、记忆检索、预算治理与输入框（Tab/折叠分区，可整体折叠）；右侧为群聊消息流 + 文件/任务/回放底部面板。
产品定位 v1.2服务电脑上的 Agent：软件首要目标是让本机 Agent（TRAE / ZCode 等）之间经此平台交流协作；内置 LLM Agent 为补充形态，外部 Agent 经接入网关进群为一等公民。
LLM 接入自定义 API：OpenAI 兼容端点（Base URL / API Key / 模型名在设置页配置），支持多模型插槽按 Agent 单独指定
身份卡编辑图形化编辑器：MVP 即提供表单式编辑（职责、工具白名单勾选、fs_scope、预算滑杆等字段化控件），附「YAML 源码」标签页支持导入导出。编辑器置于左侧栏 Tab 内
embedding 方案本地部署：本地中文友好 embedding 模型（如 bge-m3）+ Chroma / Qdrant 本地实例，记忆数据不出本机
外部 Agent 接入顺序先 TRAE 后 ZCode：第 5 步先完成 TRAE 联调，再把接线复制到 ZCode
无人值守接活可选配置项：每个外部 Agent 实例独立开关——关闭时拉取式接活（用户在场驱动）；开启时由 room-bridge 订阅总线自动唤醒认领子任务
并发写策略采用最优解：worktree 分支隔离，同一仓库多 Agent 各持独立分支，经验收流程合并

14本地 Agent 接入方案（TRAE / ZCode）

让运行在本机的既有 Agent（TRAE、ZCode 等）作为参与者进群，领取身份卡对应职责——不是重造 Agent，而是给它们一个群内工位。接入层统称「Agent 接入网关」。v1.2 定位：本机外部 Agent 是本系统的首要服务对象，本章方案是产品核心能力而非附加集成。

14.1 三种接入模式

模式适用场景接入方式唤醒机制
MCP 网关
（推荐首选）		TRAE / ZCode 本身是 MCP 客户端，零代码接线本系统以 MCP Server 身份注册进 .trae\mcp.json 与 .zcode\config.json拉取式：Agent 主动调工具收发；实时性受客户端会话驱动限制
HTTP API有编程能力的自定义 Agent 直接对接REST + SSE / 长轮询，持 ROOM_TOKEN 鉴权SSE 推送可达准实时
桥接守护进程需要无人值守、自动接活的场景每台机器跑一个 room-bridge 小进程WS 订阅 + 无头 CLI 调用，全自动唤醒
诚实说明：纯 MCP 模式下“同步收到”依赖客户端是否支持服务器主动通知及后台自主运行；若客户端由用户会话驱动才会调工具，自动性会打折。要真正全自动接活，用桥接守护进程模式。

14.2 MCP 网关设计（推荐路径）

把群聊系统包装成一个 MCP Server（本地 stdio 或远程 SSE 均可），对每个外部 Agent 暴露按其身份卡过滤后的工具视图：

// MCP 工具清单（经身份卡白名单过滤后可见）
join_room(room_id)              # 进群，声明身份
poll_messages(cursor)           # 拉取新消息（事件流游标）
send_message(type, text, refs)  # chat 互聊 / deliver 交付
claim_subtask(subtask_id)       # 认领排产单中属于自己的子任务
report_receipt(subtask_id, ok)  # 上报验收回执
query_memory(query, scope)      # scope=public|private，向量检索注入上下文
fs_read(path) / fs_write(path)  # 文件读写，走 fs_scope 边界校验

// 资源
room://{room_id}/events         # 只读事件流（供 Agent 回放上下文）
identity://{agent_id}/card      # 自身身份卡只读视图

两端各加一条配置即完成接线（字段名以各端当前文档为准）：

// TRAE： .trae\mcp.json        // ZCode： .zcode\config.json
{                                {
  "mcpServers": {                  "mcpServers": {
    "agent-room": {                  "agent-room": {
      "command": "python",             "url": "http://127.0.0.1:8899/sse",
      "args": [".../mcp_stdio.py"],    "timeoutMs": 60000,
      "env": { "ROOM_TOKEN": "***" }   "headers": { "Authorization": "Bearer ***" }
    }                                }
  }                                }
}                                }

14.3 桥接守护进程（全自动唤醒）

room-bridge 启动 → WS 订阅 wss://…/room/{id}（持 ROOM_TOKEN） │ 收到 dispatch 子任务（按绑定身份过滤） ▼ 调用本机 Agent CLI 无头执行（TRAE / ZCode 命令行模式） │ stdout 分片流式回传 send_message(type=chat) ▼ 产出文件写入挂载的工作区目录 → send_message(type=deliver) ▼ 心跳 30s 上报在线状态；收到 P0 interrupt 立即 kill 子进程

14.4 身份映射与权限继承

事项规则
实例-身份对应一个外部实例绑定一张身份卡（如 TRAE→开发员、ZCode→审稿员），群内标签同内置 Agent 一致；可在前端随时换绑
权限校验位置白名单与 fs_scope 在网关侧二次强制校验，不信任客户端自觉遵守
并发写保护两台 Agent 写同一 git 仓库时分配独立 worktree/分支，合并仍走系统的版本乐观锁与验收流程
审计外部 Agent 的全部进出消息、工具调用照常入事件流，可回放可追责
安全红线：外部 Agent 默认不授予 shell.run，确需开放逐条写进身份卡白名单；ROOM_TOKEN 按 Agent 单独发放、可单独吊销。

14.5 落地决策

  • 接入顺序：先 TRAE（MVP 第 5 步联调对象），跑通后将同一网关注册方式复制到 ZCode。
  • 无人值守为可选配置：每实例独立开关——默认关闭（拉取式，用户在场驱动）；开启后 room-bridge 订阅总线，收到 dispatch 子任务自动唤醒本机 Agent CLI 执行。
  • 并发写采用 worktree 分支隔离（最优解）：两台 Agent 写同一仓库各持独立分支，合并走版本乐观锁与验收流程。
  • v1.2 定位重申：本机外部 Agent 是系统首要服务对象——接入网关与房间总线同为 MVP 必需能力（第 12 章路线中编排闭环完成即联调网关），不是附加功能。
