# 需求澄清与提示词引导

把模糊、不完整的任务请求，通过结构化提问收敛成一份清晰、可执行的提示词与任务规格，再开始动手。

## 何时触发

当用户指令满足以下任一条件时，先澄清、后执行：

- 任务目标、对象、范围、约束、交付物、验收标准、截止时间等关键信息缺失
- 同一句话存在多种合理解读（歧义），照做可能跑偏
- 任务规模大、跨多个子系统，需要先拆解再澄清
- 用户明确要求「先澄清」「帮我理清需求」「引导我」「生成提示词」

## 澄清原则

- 一次只问一个最关键的问题，不要用问题清单轰炸用户
- 优先给出多选（A/B/C），降低用户回答成本；无法多选时再用开放式提问
- 只问会影响结果的问题，不追问无关细节
- 先问「目标与为什么」，再问「怎么做」
- 不要重复追问用户已经提供的信息

## 澄清清单（按优先级）

1. **目标**：要达成什么结果？成功的衡量标准是什么？
2. **对象与场景**：给谁用？在什么场景下使用？
3. **范围**：包含什么、明确不包含什么？边界在哪？
4. **约束**：技术栈、运行环境、时间、资源、格式限制？
5. **交付物**：最终要什么形式（文档 / 代码 / 表格 / 演示 / 图表）？
6. **验收标准**：怎样算「完成」？有哪些可检查的验收点？

## 输出：结构化提示词 / 任务规格

澄清完成后，把结论收敛成一份结构化提示词，固定包含以下字段：

- **任务目标**：一句话说明要达成的结果
- **背景上下文**：相关项目、环境、已有约定
- **明确要求**：必须满足的功能或内容要点
- **约束条件**：不可突破的限制与边界
- **交付格式**：文件类型、结构、命名、存放位置
- **验收标准**：可验证的完成条件清单

在动手前把这份规格回显给用户确认，获得确认后再执行。

## 反模式

- 不要在需求未明时直接开始实现或产出
- 不要用开放式长问题一次抛多个
- 不要漏掉验收标准——没有验收标准的任务最容易返工
- 不要为了「显得高效」跳过澄清，模糊需求是返工的最大来源
